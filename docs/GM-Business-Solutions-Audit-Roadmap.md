# GM Business Solutions — Engineering Audit & Roadmap

## Chapter 1: Introduction

GM Business Solutions is a full-stack e-commerce platform built with React and Express. The system supports customer, staff, and admin roles, product catalog management, order processing, M-Pesa payments, and customer reviews. This document records the security and engineering work completed during today's audit session, explains the reasoning behind each change, and outlines the remaining gaps that must be addressed before the application is ready for production deployment. The purpose of this documentation is to create a clear historical record of what was changed, why it was changed, and what remains to be done, so that future developers and stakeholders can understand the current state of the system without having to reverse-engineer the commit history.

## Chapter 2: Work Completed Today and Why

### 2.1 Security Hardening

Today's session began with a comprehensive security audit of both the backend and frontend codebases. The first major finding was that critical administrative and user-management routes had no authentication or role enforcement. The admin, staff, and user routers were completely open, meaning any unauthenticated visitor could read, modify, or delete records. This was addressed by applying the existing `authenticate` and `adminRoleAuth` middleware to the admins router, the staff router, and the users router. The cart router was also protected so that only authenticated users could access their cart data. For the categories router, write operations such as create, update, delete, and toggle-status were wrapped with authentication and admin role checks, while read operations remained public so that the storefront could continue to display categories without authentication. The reviews router received a similar treatment, where customers could create reviews and mark reviews as helpful, but approval, rejection, and deletion were restricted to admins only. This separation ensures that the public-facing parts of the application remain accessible while sensitive operations are properly gated.

The second major security issue was the CORS configuration, which was set to reflect any origin by using `origin: true`. This configuration allows any website on the internet to make authenticated API requests to the backend, which completely defeats the purpose of CORS-based origin restrictions. The fix involved replacing the wildcard origin with a configurable `FRONTEND_URL` environment variable that defaults to `http://localhost:5173` during development. This change ensures that only the configured frontend origin can send credentials to the API, which is essential for protecting user sessions in production.

In addition to CORS, security headers were added to every response. The `helmet` library was installed and configured to set default security headers, while explicit headers were added for `X-Frame-Options: DENY` to prevent clickjacking attacks, `Referrer-Policy: strict-origin-when-cross-origin` to control referrer leakage, `X-XSS-Protection` for legacy browser protection, and `X-Content-Type-Options: nosniff` to prevent MIME-type sniffing. Clickjacking is particularly important for an e-commerce application because an attacker could embed the site in a hidden iframe and trick an admin into clicking invisible buttons that modify orders or user roles. The referrer policy ensures that sensitive URL paths are not leaked to external sites when users navigate away from the application.

Rate limiting was added to the authentication routes using the `express-rate-limit` library. The limit was set to 20 requests per 15 minutes per IP address. This change was made to prevent brute-force attacks against the login, registration, and password reset endpoints. Without rate limiting, an attacker could attempt thousands of password guesses per minute, which is especially dangerous given that the application stores email addresses and phone numbers that could be used for targeted attacks.

The authentication system was also significantly improved by adding a refresh token endpoint with rotation. Previously, access tokens were issued with a 7-day expiration and refresh tokens with a 30-day expiration, but there was no way to actually use the refresh token to obtain a new access token. The new `/auth/refresh` endpoint accepts a refresh token, validates it against the database, and issues a new access token with a 15-minute expiration along with a new refresh token with a 7-day expiration. The old refresh token is invalidated during this process, which prevents refresh token replay attacks. The access token lifetime was reduced from 7 days to 15 minutes so that stolen tokens have a much shorter window of usefulness. Additionally, the authentication middleware was updated to validate the session token against the database on every request, which means that logging out or revoking a session takes effect immediately rather than waiting for the JWT to expire.

The global error handling was overhauled to prevent internal error details from leaking to clients. Previously, every controller had its own try-catch block that returned `res.status(400).json({ success: false, message: e.message })`, which exposed raw error messages that could contain database schema details or stack traces. All eight controller files were updated to propagate errors using `next(e)` instead, and a global error handler was added in `index.ts` that returns sanitized error responses. In production mode, the error handler returns a generic "An unexpected error occurred" message, while in development it returns the actual error message for debugging. This change prevents information leakage while maintaining debuggability during development.

### 2.2 Seed Data and Credential Hygiene

The database seed file contained hardcoded plaintext passwords and real personal email addresses. The password `password123` was used for every seed user, and the admin user was assigned the email address `moseemmanuel64@yahoo.com` while the staff user was assigned `emmanuelmose10204@gmail.com`. This is a critical security issue because anyone who reads the seed file can immediately log in as an admin or staff member, and the real email addresses could be used for social engineering or spam. The fix involved removing all hardcoded passwords and real personal emails. The seed file now accepts passwords through environment variables named `SEED_ADMIN_PASSWORD`, `SEED_CUSTOMER_PASSWORD`, and `SEED_STAFF_PASSWORD`. If these environment variables are not provided, the system generates random passwords and prints them to the console during seeding. The email addresses were changed to generic placeholder addresses such as `admin@gmnex.com` and `staff@gmnex.com`.

### 2.3 Dependency Cleanup

The backend `package.json` contained both `bcrypt` and `bcryptjs` as dependencies. Having both packages is redundant and increases the attack surface and bundle size. The `bcryptjs` dependency was removed, leaving only `bcrypt` as the hashing library. At the same time, two new dependencies were added: `helmet` for security headers and `express-rate-limit` for rate limiting. The `package.json` was also updated to reflect these changes, ensuring that the dependency tree is clean and intentional.

### 2.4 SEO Implementation

A comprehensive SEO system was implemented in the frontend using the `react-helmet-async` library. The application was wrapped with a `HelmetProvider` in `main.tsx`, and a new `SEO` component was created that dynamically sets page titles, meta descriptions, canonical URLs, Open Graph tags, Twitter Card tags, and JSON-LD structured data. The SEO component was integrated into the home page, shop page, category page, and product page. On product pages, the SEO component injects Product schema markup with price, availability, brand, and SKU information, which helps search engines understand the product data and can result in rich snippets in search results. The `index.html` file was updated with base SEO meta tags including a site description, theme color, robots directive, and canonical URL. A `robots.txt` file was added to the public folder to guide search engine crawlers and explicitly block indexing of private routes such as `/admin`, `/staff`, `/checkout`, `/account`, `/cart`, `/wishlist`, and authentication pages. A static `sitemap.xml` was also added to help search engines discover the main public pages.

### 2.5 Logo and Branding

The site logo, provided as `2.png`, was integrated across all public-facing and dashboard surfaces. The file was copied to `frontend/public/2.png` so that it can be served as a static asset. The `index.html` file was updated to use `/2.png` as the favicon and apple-touch-icon, replacing the default React favicon. The header component was updated to display the logo image instead of the text "SMARTP", with responsive sizing for mobile devices. The footer, hero section, and both the admin and staff dashboard drawers were similarly updated to display the logo image. The CSS files for these components were adjusted to style the image logos appropriately, including sizing, object-fit, and responsive breakpoints. The obsolete text-logo styles, including font-family declarations and logo-dot accent elements, were removed from the stylesheets.

### 2.6 Emoji to Icon Migration

A significant portion of the frontend was using decorative emoji characters as icons. These emojis render inconsistently across operating systems and browsers, can appear unprofessional in business contexts, and do not scale well. A batch replacement was performed across 22 components, replacing emoji characters with corresponding `lucide-react` icons. The replacements were chosen to match the semantic meaning of each emoji: phone icons for phone numbers, map-pin icons for addresses, star icons for ratings, check-circle icons for completed steps, and so on. Icon sizes were carefully chosen based on context, with 14-pixel icons for inline announcement bar elements, 16 to 18-pixel icons for card content and form steps, 20-pixel icons for dashboard statistics, and 32 to 48-pixel icons for empty states. This change gives the application a consistent, professional appearance that matches the SMARTP brand identity.

### 2.7 Vercel Deployment Configuration

A `vercel.json` file was added to the frontend to solve a 404 error that occurs on Vercel when users navigate directly to client-side routes. Vercel's default behavior is to serve static files from the output directory, and when a request comes in for a route like `/product/iphone-15`, Vercel looks for a physical file at that path and returns 404 when it does not find one. The `vercel.json` configuration adds a rewrite rule that directs all requests to `index.html`, allowing the React Router to handle the routing client-side. This is a standard configuration for single-page applications deployed on Vercel.

### 2.8 Hydration Error Fixes

During the audit, it was discovered that the admin and staff dashboard components were accessing `window.innerWidth` directly during the initial render. This causes React hydration mismatches because the server-rendered HTML does not include the correct mobile state, and the client-side render computes a different value. The fix involved changing the initial state of `isMobile` from `window.innerWidth < 768` to `false`, and then calling `handleResize()` inside a `useEffect` hook on mount to set the correct value before any client-side interactions occur. This ensures that the server-rendered markup matches the initial client render, eliminating hydration warnings and preventing layout shifts.

## Chapter 3: Remaining Gaps and Why They Matter

### 3.1 Frontend Resilience

The frontend currently has no error boundaries. In React, an error boundary is a component that catches JavaScript errors anywhere in its child component tree, logs those errors, and displays a fallback UI instead of crashing the entire application. Without error boundaries, a single unhandled exception in a product card or a dashboard widget will blank the entire page, forcing the user to refresh. This is especially problematic in production where users expect reliability. Error boundaries should be placed at the route level around each page component and at the dashboard level around the outlet in the admin and staff shells.

The application also lacks frontend route guards. While the backend enforces authentication and role requirements for API endpoints, the frontend routes for `/admin` and `/staff` are accessible to anyone who types the URL into their browser. A user who is not logged in as an admin can navigate to `/admin` and will see a broken or blank page because the dashboard components expect data that requires authentication. Route guards should be implemented as wrapper components that check the authentication context and redirect unauthenticated or unauthorized users to the login page or home page.

Form validation is another area that needs improvement. Currently, forms rely on HTML5 attributes such as `required` and `type="email"` for basic validation, but there is no schema-level validation, no real-time feedback, and no protection against malformed or malicious input. For a production e-commerce application, this is risky because bad data can reach the backend and cause errors or data corruption. Implementing a validation library with a form management library would catch errors on the client side before they reach the server, improving both security and user experience.

### 3.2 Backend Robustness

The backend lacks a request validation library. Every controller performs ad-hoc checks on request parameters, and there is no centralized schema enforcement. This leads to inconsistent validation across endpoints and makes it easy for malformed requests to slip through. A library such as `zod` or `express-validator` would allow each route to declare its expected input schema, automatically reject invalid requests with clear error messages, and protect the database from bad data.

Structured logging is absent from the backend. The current approach uses `console.error` scattered throughout the controllers and services, which makes it difficult to trace requests, debug production issues, or correlate errors with specific users or transactions. A structured logger such as `pino` or `winston` would produce JSON log output with request IDs, timestamps, user identifiers, and error stack traces. This is essential for diagnosing problems in production and for compliance with logging requirements.

The backend does not expose a health check endpoint. Health checks are used by deployment platforms, load balancers, and monitoring tools to determine whether the application is running and ready to accept traffic. Without a dedicated health check route, there is no reliable way to automate health monitoring or to configure zero-downtime deployments.

The M-Pesa callback handler currently lacks idempotency protection. When Safaricom sends a payment callback, the handler processes the payment and updates the order status. However, if Safaricom retries the callback due to a timeout or network issue, the handler will process the same payment again, potentially double-crediting the order or creating duplicate payment records. An idempotency check using the `CheckoutRequestID` would ensure that each callback is processed exactly once.

### 3.3 SEO and Marketing Readiness

The current sitemap is static and hardcoded. It lists the home page, shop page, and a few category URLs, but it does not include product pages, which are the most important URLs for an e-commerce site. As products are added or removed, the sitemap will quickly become outdated. A dynamic sitemap that is generated at build time or served from an API endpoint would ensure that search engines always have an accurate inventory of indexable pages.

The Open Graph image referenced in the SEO component is missing from the `public` folder. When links to the site are shared on social media platforms such as Facebook, Twitter, and LinkedIn, the absence of an OG image means the share will appear as a plain text link without visual appeal. This reduces click-through rates from social media. A 1200 by 630 pixel OG image should be created and placed in `public/og-image.png`.

The application does not have privacy policy or terms and conditions pages. These pages are legally required for e-commerce operations, especially when processing payments through M-Pesa and collecting personal information from customers. They are also required by Google Search Console and by most payment processors. The privacy policy should explain what data is collected, how it is used, and how users can request deletion. The terms and conditions should outline the rules for using the platform, purchasing products, and resolving disputes.

### 3.4 Monitoring and Operations

The application currently has no monitoring, alerting, or observability tooling. There is no way to know if the server is experiencing high error rates, slow response times, or resource exhaustion without manually checking the server. For a production e-commerce platform, this is unacceptable because downtime directly translates to lost revenue. Basic monitoring should include uptime checks, error rate alerts, response time tracking, and database connection monitoring.

There is no CI/CD pipeline configured. Every deployment is manual, which increases the risk of human error and makes it difficult to roll back changes quickly if something goes wrong. A GitHub Actions workflow or similar CI/CD pipeline would automate testing, building, and deployment, ensuring that every change goes through a consistent process before reaching production.

## Chapter 4: Roadmap and Implementation Order

### 4.1 Immediate Priorities Before Launch

The most critical gaps to address before the application can be considered production-ready are the frontend route guards, backend environment validation, privacy and legal pages, error boundaries, backend request validation, the missing OG image, and M-Pesa callback idempotency. Frontend route guards are essential because the admin and staff dashboards are currently accessible to unauthenticated users, which not only creates a poor user experience but also exposes the structure of the administrative interface to the public. Backend environment validation is necessary because the application currently fails silently or with confusing errors when required environment variables are missing. A startup check that validates all required variables and exits with a clear message prevents the server from starting in a broken state.

Privacy policy and terms pages are not optional for a payment-enabled e-commerce site. They are required by law in most jurisdictions, by payment processors such as Safaricom, and by app stores if the application is ever packaged for mobile. These pages should be created as public routes and linked in the footer. Error boundaries are needed to prevent single component failures from taking down the entire application. Backend request validation with `zod` will protect the API from malformed input and reduce the number of error responses generated by the server. The missing OG image should be created and added to the public folder so that social media shares look professional. M-Pesa callback idempotency should be implemented before any real money transactions are processed, to prevent double-charging customers.

### 4.2 Short-Term Improvements

Within the first week of launch, the focus should shift to form validation, structured logging, loading skeletons, content security policy, and a health check endpoint. Form validation on the frontend will improve the user experience by providing real-time feedback on invalid inputs and will reduce the number of invalid requests reaching the backend. Structured logging on the backend will make it possible to debug production issues quickly and will provide an audit trail for security events. Loading skeletons should replace the generic loader component to improve perceived performance and reduce layout shifts during data fetching.

The content security policy should be enabled in `helmet` for production. The current configuration disables CSP because it would break the application in its current state, but before launch the policy should be carefully configured to allow scripts from the application's own origin, styles from trusted sources, and images from the CDN and data URLs used by the application. A health check endpoint should be added to the backend to support deployment platform health checks and uptime monitoring. The endpoint should verify that the database connection is healthy and that critical dependencies such as the email service are reachable.

### 4.3 Medium-Term Enhancements

Over the first month of operation, the team should focus on adding automated tests, lazy loading for dashboard routes, image optimization, analytics integration, dynamic sitemap generation, and a CI/CD pipeline. Automated tests are important for maintaining code quality as the application grows. The backend should have unit tests for service functions and integration tests for API endpoints. The frontend should have tests for critical user flows such as login, registration, product browsing, and checkout. Lazy loading dashboard routes will reduce the initial bundle size and improve load times for first-time visitors, since most visitors will never access the admin or staff dashboards.

Image optimization will improve page load speeds and reduce bandwidth costs. Product images should be served in modern formats such as WebP, with appropriate sizing for different screen densities. A CDN or image transformation service can handle this automatically. Google Analytics and Google Search Console should be integrated to track user behavior, measure conversion rates, and monitor search performance. The static sitemap should be replaced with a dynamic generation strategy that includes all published products and categories. Finally, a CI/CD pipeline should be set up to automate testing and deployment, reducing manual errors and ensuring that every release goes through the same quality checks.

### 4.4 Long-Term Vision

Beyond the immediate launch requirements, the application has several strategic opportunities for growth. The current architecture is well-suited for scaling because the backend is already structured as a modular monolith with clear separation between routes, controllers, services, and data access. As the product catalog and user base grow, the team can consider extracting high-traffic services such as product search and recommendations into separate microservices. The M-Pesa integration could be extended to support additional payment methods such as credit cards, Airtel Money, and PayPal. The review and rating system could be enhanced with image uploads, verified purchase badges, and helpfulness voting. The administrative dashboards could be enhanced with advanced analytics, predictive inventory management, and automated marketing tools such as abandoned cart recovery and email campaign management.

The most important principle guiding all of these changes is that the application must remain maintainable, secure, and performant as it scales. The security hardening completed today establishes a strong foundation, but security is not a one-time activity. Regular audits, dependency updates, and penetration testing should be part of the ongoing development process. Similarly, performance monitoring and user feedback should drive continuous improvement of the user experience. The documentation produced today provides a clear baseline from which the team can measure progress and prioritize future work.
